## P1

### 1. Zero disabled the operator daily ceiling

Fixed in `79f3f99`. A wallet cap of `0` now means "no spending", and `null` removes the wallet's own cap. The effective cap is the tighter of the operator ceiling and the wallet cap, so a wallet can lower or stop its spending but never lift the ceiling. An operator ceiling of `0` stops everyone. Pending reservations count against the cap. `GET /v1/balance` shows both caps and whether spending is stopped.

Tests: `test/unit/daily-cap.test.ts`, `test/integration/caps.test.ts` (the public endpoint), audit check 4.

### 2. Concurrent top-ups exceeded the client's total budget

Fixed in `b982799`. The client counts a top-up against `maxSpendUsd` in the same tick as the check, before signing. It returns the amount only if signing fails, because then no authorization exists, and keeps it counted if the response is lost. Top-ups run one at a time: a call that waited for another top-up retries with the new balance before paying. The counter is per client instance by default; `initialSpentMicros` and `onSpendChange` make it durable, and the MCP bridge persists it to `ODOMETER_SPEND_FILE`. `maxTopupUsd` is also enforced through the SDK's spend controls.

Tests: `test/unit/client-budget.test.ts`, audit check 1.

### 3. Revocation did not revoke remote MCP spending

Fixed in `58cd62c`. An MCP session id is no longer a wallet credential:

- A session binding records the wallet, its session epoch, the IP that paid, an absolute expiry, and a voucher equal to what the session paid.
- Every paid call re-checks the epoch, expiry and IP. Revocation, through the endpoint or straight in the ledger, stops the next call, which is asked to pay again.
- `POST /v1/session/revoke` also closes the wallet's MCP sessions at once.
- A bare session id spends only its voucher. Spending the wallet's full balance needs a session token in `Authorization`, which dies with revocation.
- Session creation is rate-limited per IP and capped in total. Tool calls accept `maxPriceUsd` and `idempotencyKey`, like HTTP.

Tests: `test/integration/remote-mcp.test.ts` (8 cases including the reviewed bypass), audit check 5.

### 4. Manual recovery was not linked to the original receipt

Fixed in `050d76f`, with the ledger-level guard added in `211adc1`.

- **Ambiguous settlements are classified.** A timeout, `settlement_pending`, or a broadcast transaction that did not confirm marks the top-up `needs_review` with its signature and payer, and freezes it. Resending the same payment is refused (`payment_under_review`) and is never settled twice. A definitive failure stays retryable.
- **Recovery is one action on the original receipt.** `GET /admin/topups/{id}/verify` reads the transaction from the chain: finalized, successful, the amount received by `PAYTO_ADDRESS`, and the payer. `POST /admin/topups/{id}/resolve` credits the receipt once, with the receipt's own amount, after checking network, asset, amount and payer against that evidence. A late completion or replay of the same payload or signature then credits nothing. A payment that settles after an operator rejection goes back to review instead of crediting.
- **Generic adjustments cannot recover a payment.** The ledger itself refuses a manual credit while a top-up that could credit the wallet is settling or under review. The admin endpoint answers 409 `unresolved_topups`; `acknowledgeUnresolvedTopups` exists only for credits unrelated to a top-up.
- **The runbook** in `docs/OPERATIONS.md` is rewritten around verify and resolve.

Tests: `test/unit/topup-recovery.test.ts`, `test/integration/topup-recovery.test.ts` (including delayed completion after resolution), the e2e case that verifies a real settled top-up on-chain, and audit checks 2 and 3.

### 5. "Failed calls are never charged" was false

Fixed in `3dfa9db`, choosing the second contract the review offered. Gateway and upstream delivery failures are unbilled. Valid RPC answers are billed, including the listed client errors. A charged `sendTransaction` means the RPC accepted the transaction, not that it landed. RPC charges, top-up settlement fees and Solana fees, priority fees and tips are separate. One definition (`src/pricing/billing.ts`) feeds `/pricing` (with the exact billed codes, derived from the router's own list), `llms.txt` and the MCP tool descriptions. The README, architecture notes and pitch draft use the same wording.

Tests: `test/integration/billing.test.ts`.

## P2

### Debit and replay receipt were separate commits

Fixed in `58cd62c` (ledger) and `211adc1` (wiring and tests):

- **Atomic receipt.** The debit and the idempotency receipt are written in one SQLite transaction. A failure in either rolls back both, shown by injecting a failing trigger at the receipt write. A charged request whose handler then fails keeps a "failed after charge" receipt, so it can never be charged twice.
- **Restart recovery.** Every open reservation is released uncharged, whatever its timestamp, and in-flight idempotency keys are marked aborted, so the same key runs again. The new crash tests found that the first version missed reservations made in the same millisecond as recovery (and would miss any after a backward clock step).
- **Receipt lookup.** `GET /v1/receipts` answers whether a request was charged, by `X-Odometer-Request-Id` or `Idempotency-Key`, within configurable retention (`IDEMPOTENCY_RETENTION_HOURS`, `RESERVATION_RETENTION_DAYS`).

Tests: `test/unit/crash-recovery.test.ts` (file-backed: interrupted request, charge plus receipt across a restart, injected receipt failure, charged-then-failed handler), `test/integration/operations.test.ts` (receipts over HTTP).

### Local ledger consistency is not on-chain reconciliation

Fixed in `211adc1`:

- **Unresolved top-ups are a liability.** `reconcile()` reports `arithmeticOk`, `unresolvedTopups` (count and amount), `pendingRefunds` and `liabilitiesMicros` separately, and `ok` is false while any top-up outcome is unknown.
- **Custody is checked on-chain.** `GET /admin/readiness` reads the operator's holdings and compares them with liabilities. The holdings are read at `confirmed`, the commitment at which top-ups are credited; the e2e run showed that `finalized` lags enough to report a false shortfall right after a top-up. It also requires the associated token account that x402 payments go to.
- **Alerts have a delivery path.** `ALERT_WEBHOOK_URL` receives unknown settlement outcomes, settled-but-unrecorded credits, arithmetic mismatches, unresolved top-ups and a lost writer lock, deduplicated per key. Every alert is also logged.
- **One writer.** A heartbeated lock refuses a second gateway process on the same database, and a process that loses the lock alerts and exits. Startup recovery therefore never releases another live process's reservations.
- **Refunds stay operator-mediated payouts**, as documented.

Tests: `test/unit/crash-recovery.test.ts` (settlement in progress at a crash becomes unresolved, a pending refund stays owed across a restart, backup and restore with an open reservation, writer-lock contention and stale handover), `test/unit/alerts.test.ts`, `test/integration/operations.test.ts` (custody shortfall, missing token account, funds outside the ATA, unresolved settlement with a critical alert delivered to a webhook, a second process refused), and the e2e custody check against the validator.

### CI should fail if e2e skips

Fixed in `1f6ea84`. The e2e job sets `E2E_REQUIRE_VALIDATOR=1`, prints the validator version and uses the verbose reporter. Locally, the suite still skips without a validator.

## Launch checks the gateway can now verify itself

`GET /admin/readiness` (`211adc1`, fee payer and TLS in `464558d`) covers the review's "verify before taking deposits" list where software can:

| Review item | Check |
|---|---|
| Mainnet mint and network | `network`: mainnet USDC, else a warning |
| Recipient ATA | `custody`: the associated token account exists |
| Fee payer | `facilitator`: synced, and it offers a Solana fee payer |
| TLS | `public_origin`: HTTPS (required on mainnet) |
| Secrets | `session_secret` |
| Persistent storage | `storage` |
| Alerts | `alerts`: a webhook is set |
| Custody | `custody`: holdings at `confirmed` at least balances plus pending refunds |
| Unresolved settlements | `unresolved_topups` |
| Single writer | `writer_lock` |

Restores are documented as a procedure (`docs/OPERATIONS.md`, "Restoring") and tested at the ledger level; a restore drill on the real deployment is still a human step. Proxy trust (`TRUST_PROXY`) and the refund policy are documented, not checked.

## Other review points

- **Neutral name.** `SERVICE_NAME` now drives every public surface: paywall page, index, `llms.txt`, SIWx sign-in statement, Bazaar metadata and MCP server ids. The default stays the owner's chosen project name. Readiness warns while the public name contains "Helius", so a deployment cannot use it unnoticed.
- **Benchmark with identical commitment** (`b26b027`). Every tier now injects `confirmed` when a request sets none (fast used to inherit the upstream default, usually `finalized`), and every built-in benchmark workload pins `confirmed`.
- **sendTransaction** stays disabled by default; nothing rebuilds or re-signs transactions.
- **Bazaar** discovery metadata is off unless `BAZAAR_DISCOVERY=true`, and readiness warns when it is on.

## Follow-up finding: simultaneous MCP calls exceeded the session allowance

A deeper review found a launch blocker in the fix for finding 3. A bare MCP session id is limited to what the session paid, but the allowance was checked before the call and reduced only after it finished. Calls sent at the same time each passed the check against the same allowance, so a session could overspend it and draw on funds the wallet had deposited earlier. Reproduced locally with fake money: 7 of 12 simultaneous calls succeeded on a session that had paid for 2.

Fixed: the price is now held from the session's allowance in the same tick as the check, before any await, and only the unused part is returned when the call resolves (all of it for a call that is not charged). The hold and its return go to the binding that was checked, even if the session is rebound meanwhile.

Tests: `test/integration/remote-mcp.test.ts`, "simultaneous calls cannot exceed what the session paid or reach older wallet funds" and "a failed call returns its hold to the session allowance".
